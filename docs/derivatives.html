Chapter 04

Differentiating the network itself

To ask whether a curve obeys an equation, you need its slope and its bend, exactly and at any point.

The equation contains x′ and x″. A network outputs x. The bridge is that a network is a composition of simple functions, so the chain rule gives its derivatives exactly.

Two different derivatives are involved, and mixing them up is the most common confusion about PINNs.

  • With respect to the input: how the position changes when time changes. These are x′ and x″, and they go into the loss.
  • With respect to the weights: how the loss changes when a weight changes. This is ordinary backpropagation, and it goes to the optimiser.

A PINN takes the first kind, builds a loss from it, then takes the second kind of that loss. Training therefore needs derivatives of a derivative of a derivative.

In PyTorch

pinn/derivatives.pythe core of it
t = t.detach().clone().requires_grad_(True)
x = net(t)
v = _slope(x, t)
a = _slope(v, t)

requires_grad_(True) is on the time, which is what makes autograd record how the output depends on it. detach().clone() makes a private copy, so the caller's tensor is not changed as a side effect.

torch.autograd.grad differentiates a scalar, and x has one entry for each time. Passing grad_outputs=torch.ones_like(y) differentiates the sum of all entries. That is safe here because x[i] depends only on t[i], so the derivative of the sum with respect to t[i] is the derivative of x[i] alone. Batch normalisation would break this, since it lets one row of a batch affect another. the call

create_graph=True is the argument that matters most. It records the differentiation itself, so the result can be differentiated again. Remove it and v is a plain table of numbers with no history. The second call then has nothing to walk back through. If only the second call lacked it, the loss would still compute, and no gradient from x″ would reach the weights. a test guards this.

Why not finite differences?

The second difference, (x(t+h) − 2x(t) + x(t−h)) / h², subtracts nearly equal numbers and divides by something tiny. A large h gives truncation error and a small h gives rounding error. Autograd has neither. The tests still use finite differences as an independent check, with loose tolerances, because a method that shares no code with the thing being tested is the best kind of test.

The activation has to bend

The second derivative of the network is built from the second derivative of its activation. If that is zero, the mass term vanishes from the equation, whatever the weights are.

With ReLU the result is a wrong answer that arrives without an error message: m x″ is zero, the remaining terms ask for c x′ + k x = 0, and the network goes after that. Its solutions decay like e−75t, so the trained network is almost exactly zero. The measured error is 0.078, the same as always answering zero, against 3.6 × 10−6 for tanh. the test that records it

A second failure turned up in testing. A straight line has a constant slope, and a constant has no graph, so asking for its derivative raised a RuntimeError. The fix is two lines: if there is nothing to differentiate, the answer is zero.

IN:What does create_graph=True do, and what breaks without it?
OUT:

Autograd normally frees the graph after a backward pass and returns the gradient as plain numbers. With create_graph=True the gradient is itself part of a graph. A PINN needs that twice: once to differentiate x′ into x″, and once because the loss contains x″ and has to send gradients through it to the weights. Without it, the second derivative can't be taken, or the physics term stops teaching the network anything.
